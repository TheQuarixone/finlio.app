# Local Supabase — development setup

Run a full Supabase stack (Postgres, Auth, Storage, Studio) on your machine and
apply our **Drizzle** migrations against it. This is the dev database for Phase 1
(the `subscribers` waitlist table) and everything after.

> Local Supabase is for **development only**. Prod and preview run on hosted
> Supabase projects (see [`TECHSTACK.md`](./TECHSTACK.md) §9). Never point local
> tooling at prod credentials.

---

## 1. Prerequisites

- **Docker Desktop** running (the local stack runs in containers).
- **Supabase CLI** — install once:

```bash
# macOS (Homebrew)
brew install supabase/tap/supabase

# or, no global install, per-repo via npx
npx supabase --version
```

- Workspace deps installed (`pnpm install` at the repo root) — this pulls in
  `drizzle-kit`.

---

## 2. One-command start

From the repo root:

```bash
supabase start
```

First run pulls the container images (a few minutes); later runs are fast. When it
finishes it prints local credentials — keep these handy:

- **API URL** — `http://127.0.0.1:54321`
- **DB URL** — `postgresql://postgres:postgres@127.0.0.1:54322/postgres`
- **Studio** — `http://127.0.0.1:54323` (browse tables/data)
- **publishable key** / **secret key** — printed in the same output

Re-print them anytime with:

```bash
supabase status
```

> If `supabase/` doesn't exist yet in the repo, run `supabase init` once first
> (commits a `supabase/config.toml`), then `supabase start`.

---

## 3. Point the app at local

Add these to `apps/web/.env.local` (never commit real values — see
`apps/web/.env.example`):

```bash
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable key from `supabase status`>
SUPABASE_SECRET_KEY=<secret key from `supabase status`>

# Drizzle talks straight to Postgres:
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
DIRECT_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

Locally the pooled and direct URLs are the same; on hosted Supabase `DATABASE_URL`
is the pooled connection and `DIRECT_URL` is the direct one used by drizzle-kit for
migrations.

---

## 4. Apply Drizzle migrations

Our schema lives in TypeScript and migrations are generated by drizzle-kit:

```bash
# after editing the schema, generate a new SQL migration
pnpm --filter web db:generate

# apply pending migrations to the local DB
pnpm --filter web db:migrate

# open Drizzle Studio to inspect data (alternative to Supabase Studio)
pnpm --filter web db:studio
```

Commit the generated migration files with the schema change in the same PR. CI
applies the same migrations against the preview DB.

---

## 5. Everyday commands

```bash
supabase start      # boot the local stack
supabase stop       # stop it (keeps data)
supabase status     # show URLs + keys
supabase db reset   # drop + recreate the local DB, re-run migrations (+ seed)
```

Use `supabase db reset` when your local DB drifts or you want a clean slate — it
rebuilds from migrations, so it's safe and repeatable.

---

## 6. Seeding (optional)

Put SQL in `supabase/seed.sql` to preload dev data (e.g. a few `subscribers`
rows). `supabase db reset` runs it automatically after migrations.

---

## 7. Troubleshooting

- **Port already in use** — another `supabase start` or a stray Postgres is
  running. `supabase stop`, then retry; or free the port (`54321`–`54323`).
- **Docker not running** — start Docker Desktop first.
- **Migrations out of sync** — `supabase db reset` to rebuild from migrations.
- **Studio shows no tables** — you haven't run `pnpm --filter web db:migrate` yet.
